Load Balancers, Service Discovery & Service Meshes

How infrastructure keeps services connected while they evolve

⏱ ~15 min read 🔗 Encoding & Evolution 🏗 Infrastructure

Applications change. New features ship, schemas evolve, APIs gain new fields. But in a live system, you can't swap every server simultaneously — you need to deploy gradually while the system keeps serving traffic. This creates a fundamental tension: at any given moment, your infrastructure might be running two versions of the same service at once.

This article builds from the ground up. We'll quickly cover why encoding formats matter, what backward and forward compatibility mean, and how data flows between services. Then we'll arrive at the real question this chapter builds toward: once you have rolling upgrades and mixed-version deployments, how does the network infrastructure route requests to the right version?

Background · 1 of 3

Encoding Formats

In memory, data lives as objects, structs, and lists. When you send data over the network or write it to disk, it must become a flat sequence of bytes. The translation is called encoding (or serialization). Choosing an encoding format is a decision that reverberates through your system's evolvability.

Text formats — JSON, XML, CSV

Human-readable, widely supported. Schema is optional, which is flexible but means field names are repeated in every message. Numbers can be ambiguous (no integer vs float distinction in JSON).

Binary schema-driven — Protobuf, Avro

Compact: field names are replaced by numeric tags (Protobuf) or removed entirely (Avro). Require a schema, which doubles as documentation and enables tooling for compatibility checks.

When a schema changes, two things must hold for the system to keep working during a transition:

✅ Backward compat
New code reads old data. Usually easy — new code knows what old fields look like.
✅ Same version
No compatibility needed.
Old Code reads
✅ Same version
No compatibility needed.
⚠️ Forward compat
Old code reads data written by new code. Harder — old code must gracefully ignore unknown fields.

Protocol Buffers achieves forward compatibility with field tags: unknown tag numbers are skipped, not rejected. Avro resolves by matching fields by name between writer's and reader's schema — extra fields are ignored, missing fields use defaults.

Key insight In a rolling upgrade, you need both. Old nodes read new messages (forward compat) and new nodes read old messages (backward compat). Pick a format that handles both explicitly.

Modes of Dataflow

Encoded bytes travel between processes in three main ways. Each mode has different compatibility pressures:

🗄️

Through Databases

Writer encodes, reader decodes — possibly months later. Data outlives code, so both backward and forward compat are required.

🌐

REST & RPC

Client encodes request, server decodes it. Usually safe to assume servers are updated first, so forward compat on requests matters most.

📨

Message Brokers

Producer encodes, consumer decodes asynchronously. Messages can be re-read later — schema compatibility needs careful management.

We're focusing on REST & RPC. This is where service discovery and load balancing live — which brings us to the core of this article.

The Bridge

The Rolling Upgrade Challenge

When you deploy a new version of a service in production, you don't swap every instance at once. Instead, you do a rolling upgrade: replace one node at a time, verify it runs smoothly, and proceed. This approach avoids downtime and limits blast radius if something goes wrong.

During a rolling upgrade, old and new versions of your service run simultaneously — and they must both be able to handle requests.

This is where encoding meets infrastructure. Format-level compatibility (Protobuf, Avro) ensures that old and new code can parse each other's messages. But there's a second, infrastructure-level question: how does a request get routed to the right instance? If a v2 client sends a request with a new field, you want it to reach a v2 server. If a v1 client can only speak the old protocol, you might want to route it to a v1 server until both sides upgrade.

Load balancers and service discovery systems are the infrastructure layer that makes this routing possible. That's why this topic appears here, in a chapter about encoding and evolution.

Main Topic

Load Balancing Approaches

When multiple instances of a service run simultaneously, incoming requests must be distributed across them. This is load balancing. But to balance load, clients first need to know which instances exist and where they are — that's service discovery. Five main approaches solve these problems, each with different trade-offs.

Hardware Load Balancers

The oldest solution: a dedicated physical appliance installed in the datacenter. Clients connect to a single virtual IP (VIP) address and port. The hardware device intercepts every connection and forwards it to one of the backend servers according to a load distribution algorithm (round-robin, least-connections, etc.).

Hardware LBs operate at layer 4 (TCP/UDP) or layer 7 (HTTP). Layer 4 devices are faster but opaque — they can't inspect request content. Layer 7 devices can route based on HTTP headers, paths, or cookies, enabling sophisticated traffic shaping.

The appliance continuously health-checks its pool of servers. If a server stops responding, the LB automatically removes it from rotation — clients never notice the failure.

Strengths

  • Extremely high throughput (line-rate forwarding)
  • Automatic failure detection & failover
  • Single VIP — clients need zero configuration
  • Proven technology, decades of vendor support

Limitations

  • Expensive — six-figure appliances are common
  • Vendor lock-in and slow upgrade cycles
  • Single point of failure without HA pairing
  • Scaling requires more hardware, not more code

When to use On-premise datacenters with high-throughput, latency-sensitive services (financial systems, telecoms) where budget allows dedicated appliances.

Software Load Balancers

Software load balancers like NGINX and HAProxy provide the same logical topology as hardware LBs — a single entry point that distributes traffic across a pool of servers — but run as ordinary applications on commodity hardware.

NGINX and HAProxy operate at layer 7 and support HTTP, TCP, and UDP. They can route based on request path, hostname, headers, or cookies, making them powerful for microservice architectures. For example, you can route /api/v1/* to old servers and /api/v2/* to new servers — directly supporting the mixed-version scenario from rolling upgrades.

Because they run on standard machines, software LBs can be horizontally scaled, run in containers, and configured through code. The backend server pool is defined in a config file that can be reloaded without downtime.

Strengths

  • Runs on any commodity hardware or VM
  • Config-as-code, hot-reload without downtime
  • Layer 7: route by path, header, cookie
  • Vastly cheaper than hardware alternatives

Limitations

  • Backend pool is statically configured — manual updates when servers change
  • Another service to operate, monitor, and keep highly available
  • Can become a bottleneck at very high connection counts

DNS-Based Load Balancing

DNS naturally supports multiple IP addresses per hostname. By associating several server IPs with the same domain name, DNS enables a simple form of load balancing: when a client resolves api.example.com, it gets multiple IPs back and picks one (usually the first, though some clients rotate).

There's no dedicated LB appliance. The DNS server is the distributor. This makes DNS load balancing incredibly cheap — the only requirement is a DNS server configuration change.

The staleness problem DNS entries are cached at every layer: the resolver, the OS, the browser. A removed server's IP can remain in caches for the full TTL duration (minutes to hours). If a server goes down, clients with stale cache entries will fail to connect until the cache expires.

Strengths

  • Zero infrastructure cost — DNS server already exists
  • Works at any scale (anycast routing in cloud CDNs)
  • Geo-routing by region is straightforward

Limitations

  • Staleness: client cache keeps dead IPs for full TTL
  • No health-checking built in (without extra tooling)
  • Poor fit for fast-changing environments (Kubernetes)
  • No request-level routing — just connection distribution

Service Discovery Systems

Service discovery replaces DNS with a purpose-built registry that understands the lifecycle of service instances. Tools like etcd and Apache ZooKeeper maintain a live, consistent view of which service instances are healthy and accepting requests.

When a service starts, it registers itself: "I'm Server B, listening on 10.0.0.2:8080, shard=3, datacenter=us-east-1." It then continuously sends heartbeat signals to the registry. If heartbeats stop, the registry marks the instance as unavailable — within seconds, not minutes.

Clients query the registry directly before connecting. Unlike DNS, clients get rich metadata: version, shard, region. This enables smart load balancing — a v2 client can query "give me all v2 server instances" and connect only to compatible ones.

Strengths

  • Real-time view of healthy instances (seconds, not minutes)
  • Rich metadata enables smart routing (version, region, shard)
  • Supports highly dynamic environments (containers, Kubernetes)
  • Client-side load balancing — no single LB bottleneck

Limitations

  • Another distributed system to operate (etcd, ZooKeeper are complex)
  • Clients must include discovery library code
  • Registry becomes a consistency-critical component

Service Meshes

A service mesh takes the capabilities of software load balancers and service discovery and moves them out of application code entirely. Instead of each service embedding a discovery library, a lightweight sidecar proxy runs alongside every service instance — as a separate process or container. All network traffic is transparently intercepted by the sidecar.

The sidecar is configured by a control plane (Istio's istiod or Linkerd's control plane). When Service A wants to call Service B, A's sidecar consults the control plane for routing rules and healthy endpoints, then establishes a mutual TLS (mTLS) connection directly to B's sidecar. The actual services only ever talk to their local sidecar over localhost.

This topology has a powerful consequence: since all inter-service communication flows through the sidecars, the mesh automatically provides encryption (mTLS), traffic metrics, distributed tracing, circuit breaking, and retries — without any application code changes.

Strengths

  • Encryption (mTLS), observability, retries — zero app code changes
  • Fine-grained traffic control: canary deploys, A/B testing, weight-based routing
  • Uniform policy enforcement across all services
  • Perfect for Kubernetes environments

Limitations

  • Added latency per request (two extra hops through sidecars)
  • Significant operational complexity — control plane must stay healthy
  • Resource overhead: every pod runs an extra proxy container
  • Steep learning curve (Istio is notoriously complex)

Canary deploys with a service mesh You can route 5% of traffic to v2 servers while keeping 95% on v1 — a perfect complement to rolling upgrades. The mesh enforces the split at the network level without any application changes.

Choosing the Right Approach

No single solution fits every environment. The right choice depends on how dynamic your infrastructure is, what orchestration platform you use, and how much operational complexity you can absorb.

Closing thought

Load balancing, service discovery, and service meshes aren't separate infrastructure concerns — they're the network-layer expression of the same encoding compatibility problem. When your format ensures backward/forward compat, any instance can handle any request. When your load balancer routes requests intelligently, you can run old and new versions simultaneously without client disruption. Together, these two layers make rolling upgrades safe, routine, and — eventually — invisible to the outside world.
